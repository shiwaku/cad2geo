# 評価: dwg2geo v0.2.5

実施: 2026-10-12 / 対象: [dwg2geo](https://github.com/milkway/dwg2geo) v0.2.5（Windows 用ビルド済みバイナリ、`native-backend` 入り、`native-reproject` なし）

設計書「先行例: dwg2geo」の判断材料として、実在する建築図面で dwg2geo を試した。

## 1. 入力

米子コンベンションセンター（ビッグシップ）の施設図面 DXF 3 枚（取得方法は [testdata/README.md](../testdata/README.md)）を、ODA File Converter 27.9.0 で DWG に変換した 6 ファイル。

| 元の DXF | 図面 | `$ACADVER` | 文字コード | `$INSUNITS` | 変換した DWG |
|---|---|---|---|---|---|
| `12f-heimenhall.dxf` | 全体平面図 1F・2F | AC1009（R12） | 記録なし（cp932） | なし | AC1032 / AC1015 |
| `entoransurobi.dxf` | エントランスロビー | AC1015（2000） | ANSI_932 | 4（mm） | AC1032 / AC1015 |
| `stage_100_1.dxf` | 多目的ホール舞台平面図 | AC1024（2010） | UTF-8 | 4（mm） | AC1032 / AC1015 |

比較のため、元の DXF を GDAL 3.13.3 の `ogr2ogr` でも GeoJSON にした。

```bash
dwg2geo inspect <dwg> --json
dwg2geo convert <dwg> -o <out.geojson> --backend native --allow-local-coordinates
```

## 2. 結果

### 2.1 読み込み

6 ファイルとも strict モードで読めた。エラー 0、未知のエンティティ 0。

| 図面 | エンティティ（モデル空間） | 内訳 |
|---|---:|---|
| 全体平面図 | 24,660 | LINE 20,982 / ARC 3,277 / TEXT 201 / CIRCLE 199 / INSERT 1 |
| エントランスロビー | 2,597 | LINE 2,139 / ARC 351 / MTEXT 52 / CIRCLE 38 / POLYLINE 6 / HATCH 5 / WIPEOUT 3 / SOLID 2 / INSERT 1 |
| 舞台平面図 | 1,533 | LINE 882 / ARC 556 / MTEXT 94 / LWPOLYLINE 1 |

**AC1032 と AC1015 の出力は、ハンドル（図面内 ID）を除いて完全に一致した。** 3 図面とも、ジオメトリと属性の組がすべて同じだった。

### 2.2 変換

- 全エンティティの行き先がレポートで説明されている（`accounting.unaccounted = 0`）
- 未対応は WIPEOUT 3 件のみで、理由とハンドルつきでレポートに出る
- ブロック展開、BYLAYER の色・線種の解決、文字の高さ・回転角が属性に入る

### 2.3 日本語

3 図面とも、TEXT / MTEXT の日本語が正しく出た（`電話コーナー`、`多目的ホール`、`天井反射板（１）` など）。

同じ図面を GDAL で DXF から読むと、3 枚中 2 枚で日本語が壊れた。

| 元の DXF | GDAL 3.13.3（DXF を直接） | dwg2geo（ODA で DWG にしたもの） |
|---|---|---|
| R12・文字コード記録なし | cp932 のバイト列をそのまま出力し、**GeoJSON として読めないファイル**になる | 正しい |
| 2000・cp932 | 正しい | 正しい |
| 2010・UTF-8（ヘッダは ANSI_932） | ヘッダを信じて cp932 として読み、`螟ｩ莠募渚...` と**文字化け** | 正しい |

ただし dwg2geo が正しく読めたのは、**ODA が DXF → DWG の変換時に文字コードを正規化したおかげ**でもある（ODA は R12 の DXF に `ANSI_932` を補った）。dwg2geo は DXF を直接読めないので（§2.5）、DXF の文字コード判定は評価できていない。

細かい差として、cp932 の `0x817C`（長音の代わりに使われがちな「－」）を、GDAL は U+2212（−）、dwg2geo は U+FF0D（－）にしている。Windows で作られた図面なら U+FF0D が妥当。

### 2.4 GDAL との図形の差（エントランスロビー）

| | 件数 | 範囲（Y の最小） |
|---|---:|---:|
| GDAL | 2,597 | −107,110 |
| dwg2geo | 2,595 | 71,704 |

差は WIPEOUT 3 件。GDAL は WIPEOUT を座標の壊れたポリゴンとして出しており、建物から 100 m 以上南に伸びている。dwg2geo は WIPEOUT を変換せず、レポートで報告している。**dwg2geo の扱いのほうが正しい。**

### 2.5 問題点

| 項目 | 内容 |
|---|---|
| **DXF を読めない** | `.dxf` を渡すと「Unsupported CAD version」で失敗する。DWG 専用 |
| **`$MEASUREMENT` の読み違い** | mm 図面（`$MEASUREMENT = 1`、メートル法）を `english` と報告する。ODA で DWG → DXF に戻すと 1 が入っているので、DWG 側は正しい。dwg2geo は acadrust 0.5.1 に固定しており、0.6.4 で追加された「AcDb:Template セクションから `$MEASUREMENT` を読む」処理が無いためと思われる（未検証）。座標系変換では `$INSUNITS` と `$MEASUREMENT` の一致を見て単位を決めるので、mm 図面で毎回 `--source-units` が要ることになる |
| **ビルド済みバイナリに座標系変換が無い** | `--source-crs` には `native-reproject` 機能と PROJ 9.6 以上が必要。WASM 版でも使えない見込み |

### 2.6 文字の揃え位置

TEXT / MTEXT の属性に、文字の揃え位置（左揃え・中央揃え・アタッチメントポイント）が無い。挿入点・高さ・回転角だけでは、左揃えの文字と中央揃えの文字を正しい位置に描けない（QGIS でラベルにすると、左揃えの表題などが左にずれて見える）。

### 2.7 対応点による位置合わせ

全体平面図を、実在する建物に合わせた。最初に OSM（基盤地図情報）を基準にし（2.7.1）、回転の誤差が見つかったので航空写真を基準にやり直した（2.7.2）。

#### 2.7.1 OSM（基盤地図情報）を基準にした位置合わせ

**対応点の取り方。** 地図側は OSM の建物外形（米子コンベンションセンターの楕円形の大ホール。出典は国土地理院の基盤地図情報 1/2500）を、平面直角座標系第 5 系（EPSG:6673）に変換して使った。図面側は 1 階の楕円部分の円弧の凸包、地図側は楕円ホールの外形に、それぞれ楕円を当てはめた。

| | 中心 | 長半径 | 短半径 | 面積 |
|---|---|---|---|---|
| 図面 1 階 | (118148, 131414) mm | 60,516 mm | 28,293 mm | 5,371 m² |
| OSM（基盤地図情報） | (−90808.7, −63800.8) m | 61.05 m | 27.49 m | 5,259 m² |

回転角の候補は 58° と −122° の 2 つで、図面で楕円の西に延びる棟が地図では北側にあることから −122° とした。楕円の長軸・短軸の両端 4 点を対応点にした。

```bash
dwg2geo convert 12f-heimenhall.dwg -o calib.geojson --backend native   --target-crs EPSG:6673   --control-point "99753.0,73761.6=-90848.152,-63754.263"   --control-point "136543.7,189067.3=-90769.231,-63847.422"   --control-point "145102.7,122814.1=-90829.666,-63818.611"   --control-point "91193.9,140014.8=-90787.717,-63783.074"
```

**結果。**

| 項目 | 値 |
|---|---|
| 縮尺 | 0.0010021（mm → m の 0.001 との差 0.2%） |
| 回転 | −122.03° |
| 残差 | RMS 0.67 m、最大 0.86 m |

地理院の写真に重ねると、大ホールの屋根・客席の向き・北東に延びる棟が一致した。残差は図面の外壁線と基盤地図情報の外形の差を表す。ただし 4 点は 1 つずつ当てはめた楕円の軸の端点で独立していないので、この残差は位置合わせの正しさの検証にはならない。実際、航空写真と重ねると、ホールから約 100 m 離れた北側（円形レストラン・北東の棟）で図面が 4〜5 m 西にずれていた。楕円ホールだけで回転を決めたための回転の誤差（約 0.9°）である。

**2 階も別に合わせた。** この図面は 1 枚に 1 階と 2 階が並んでいるので、2 階の楕円にも同じ手順で楕円を当てはめ、別の対応点で変換し直した（縮尺 0.0010061、回転 −122.24°、残差 RMS 0.60 m / 最大 0.77 m）。2 階北端の円形のレストランが、OSM（基盤地図情報）の円形の建物と一致した。

dwg2geo は 1 ファイルに 1 つの変換しか掛けられないので、階ごとに変換を 2 回実行し、位置合わせ前の図面座標で図形を 1 階（y > 60,000）・2 階・図枠に振り分け、ハンドルで各階の図形を取り出した（1 階 11,629 / 2 階 13,022 / 図枠 13）。

#### 2.7.2 航空写真を基準にした位置合わせ

基準を、G空間情報センターの鳥取県「空中写真（オルソ画像）」（公共データ利用規約 第 1.0 版）の `ap_05mb171.tif`（地上画素寸法 0.32 m、第 5 系）に替えた。6.4 GB の ZIP から 1 枚だけを `/vsizip//vsicurl/` で取り出し、表示用に [aerial-photo-tile-pipeline](https://github.com/shiwaku/aerial-photo-tile-pipeline) でタイル化した。対応点は元の GeoTIFF から求めた。

**地面の高さの点はほとんど取れない。** 1 階の平面図にあるのは壁・階段・柱で、写真では屋根と木の下に隠れる。写真に写る地面の目印（駐車場の白線、手すり）は図面に無い。そこで **2 階の平面図と写真の屋根**を対応させ、2 階から 1 階をたどることにした。

**図形の中心を対応点にした。** 屋根の張り出しは周囲にほぼ均等なので、中心を使えば打ち消される。写真側は明るい屋根の領域を自動で抜き出して当てはめた。

| 対応点 | 図面（2 階） | 写真 |
|---|---|---|
| G1 円形レストラン | 外壁の円の中心 | 白い輪（屋根の縁）に円を当てはめた中心（半径 8.85 m） |
| G2 大ホール | 外壁の楕円の中心 | 屋根の輪郭に楕円を当てはめた中心（長半径 59.6 m、短半径 27.1 m） |

**縮尺は 0.001 に固定した。** 2 点から相似変換を解くと縮尺が 0.0009827 になる（2 点間が写真で 98.61 m、図面で 100.35 m）。図面は mm で描かれており縮尺は確定しているので、この 1.7% の差は、高い大ホールの屋根の中心が倒れ込みでレストラン側に寄って写っているためと判断した。回転と平行移動だけを 2 点の最小二乗で解いた。dwg2geo は縮尺を固定できないので、この変換で計算した対応点を `--control-point` に渡した。

**1 階は柱で 2 階からたどった。** 1 階と 2 階の図面に共通する柱（半径 450 mm などの円）を最近傍で対応させ、1 階 → 2 階の剛体変換を求めた。**23 組が一致し、残差は中央値 23 mm、最大 90 mm、回転差 0.02°**。1 階の変換は、これに 2 階の変換を合成したもの。

**結果。**

| 項目 | 値 |
|---|---|
| 2 階の回転 | −123.11°（縮尺 0.001 固定） |
| 対応点の残差 | G1・G2 とも 0.87 m（2 点を結ぶ方向。大ホールの屋根の倒れ込み） |
| 検証: 大ホールの長軸の向き | 写真と図面から −122.70°（差 0.41°） |
| 検証: 北東の棟の外壁の向き | 写真の屋根の辺と図面の外壁から −123.27°（差 0.16°） |
| 1 階の回転 | −123.09° |

検証に使った 2 つの向きは、対応点とは独立に写真と図面から求めた。2.7.1 で 4〜5 m ずれていた北側の円形レストランと北東の棟が、写真の屋根と重なった。

**試してうまくいかなかった方法。** 図面の線全体と写真のエッジ（輪郭）の距離を最小にする相似変換（チャンファーマッチング）も試したが、回転が −124.9° と −127.3° に割れ、検証点の誤差も 3〜4 m から改善しなかった。写真には図面に無いエッジ（白線・手すり）が多く、図面の室内の線は屋根と対応しないためで、この図面には向かない。

**分かった制約。**

| 項目 | 内容 |
|---|---|
| **対応点を経緯度で渡すと形が歪む** | 地図側の座標は `--target-crs`（既定 EPSG:4326）の値として扱われ、相似変換もその座標のまま解く。経緯度で渡すと度の単位で回転・縮尺を解くことになり、東西方向が約 0.81 倍（米子の緯度で cos 35.4°）に潰れる。経緯度で渡すと「ありえない座標」のチェックにも掛かる。平面直角座標系で渡し（`--target-crs EPSG:6673`）、出力を別途経緯度に変換する必要がある（ビルド済みバイナリには座標系変換が無いので QGIS で変換した） |
| **1 ファイルに 1 つの変換しか掛けられない** | この図面は 1 枚に 1 階と 2 階が並んでいる。1 階に合わせると、2 階は約 130 m 西に、表題欄は道路の上に載る。図面の一部（範囲・レイヤ）ごとに別の変換を掛ける手段が無く、今回は変換を 2 回実行してハンドルで振り分けた |
| **文字の属性に位置合わせが反映されない** | 位置合わせ後も `text_rotation_deg`（文字の回転角）と `text_height`（文字高）は図面の値のまま。地図上で正しく描くには、利用側で位置合わせの回転（−122°）と縮尺（0.001）を足す必要がある |
| **縮尺を固定できない** | CAD 図面は縮尺が単位から確定しているのに、相似変換は縮尺も解く。対応点に偏りがあると縮尺がずれる（今回は 2 点で 1.7%）。縮尺を固定した変換（回転・平行移動の 3 パラメータ）を選べるとよい |
| **対応点を探す手段が無い** | 図面と地図の対応する点を見つけるのが一番手間がかかる。今回は図形の中心の自動抽出で済んだが、一般の建物では地図と図面を見比べて点を選ぶ UI が要る |

## 3. 未評価

- **座標系変換**（`--source-crs`）: ビルド済みバイナリに無い。`native-reproject` 付きでビルドしてから
- **本物の AutoCAD が書いた DWG**: 今回の DWG はすべて ODA が書いたもの。Autodesk のサンプルで試す
- **WASM 版（npm の `dwg2geo`）**

## 4. 所見

- **DWG の読み込みと変換の品質は高い。** 日本の実図面で、形式（2000 / 2018）による差がなく、日本語も正しく、未対応は明示される。GDAL より正確な点もある（WIPEOUT）
- **対応点による位置合わせの計算は、平面直角座標系で渡せば正しく動く。** 精度を決めるのは対応点の取り方で、基準を航空写真にし、図形の中心を使い、縮尺を固定することで、向きの検証で 0.2〜0.4° の一致まで詰められた
- **足りないのは設計書で挙げたとおりの部分に、評価で分かった点が加わる。**
  - DXF の入力、DXF の文字コード判定（GDAL も間違える）
  - 日本固有の対応（平面直角座標系）と、ブラウザで使える座標系変換。対応点を経緯度で受け取っても歪まないよう、内部で投影座標系に変換してから解く
  - 図面の一部（範囲・レイヤ）ごとの位置合わせと、縮尺を固定した変換
  - 文字の揃え位置の属性と、位置合わせを反映した文字の回転角・文字高
  - 地図と図面を見比べて対応点を選ぶ UI
